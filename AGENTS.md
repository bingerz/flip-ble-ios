## Learned User Preferences

- Keep the BLE core in Objective-C and improve the Swift call surface (nullability, properties, and a Swift facade) instead of rewriting the implementation. Use the pure Swift Example app as the acceptance surface.
- Extend the Swift facade so app code, including nut, can scan, connect, restore, retrieve, manage multiple devices, discover, read, write, notify, and read RSSI without calling `BZ*`. Leave auto-reconnect, auth, bonding, RSSI smoothing, and manufacturer-data parsing in the app. Keep `BLEPeripheral.peripheral` public for DFU. Do not add `Sendable` or `@MainActor` while the pod stays on Swift 5.5.
- Match the iOS Example to the Android flip-ble demo's main path: scan, connect, services, characteristics, properties, and the operation console. Do not port Android-only extras such as protocol tests, stress tests, hidden AutoConnect, bonded-device logs, the location prompt, or requesting MTU 23 after connect.
- Demo-only UI work stays in the Example. Keep those screens easy to scan and visually finished: empty states, in-page errors, readable long UUIDs, and controls that do not cover text. If a screenshot still looks unfinished, iterate the layout and copy again. Leave SDK behavior, including write type, unchanged in those passes.
- Cover new logic with simulator-runnable tests. Leave live connect, discover, read, write, and notify out of those tests; the simulator has no BLE radio and those calls hang or fail.

## Learned Workspace Facts

- Flip-BLE is the BLE SDK split out of `/Users/hanson/myWork/iOS/nut` for that app's Swift migration. The Android counterpart demo is `/Users/hanson/myWork/android/flip-ble`.
- The CocoaPods pod is `Flip-BLE` (module `Flip_BLE`), deployment target iOS 15.0, Swift 5.5. The pod version is only `s.version` in the root `Flip-BLE.podspec` (currently 0.5.2); the Example app version is separate. The core stays Objective-C (`BZCentralManager`, `BZPeripheral`, `BZPeripheralController`). Swift entry points are `BLECentral`, `BLEPeripheral`, `BLEAdvertisement`, and `BLEError`. `BLECentral` covers state, scanning, connection events (including retrieve and restore), and multi-device tracking; scan, retrieve, and connection streams share one cached `BLEPeripheral` per identifier and allow multiple subscribers, and retrieve does not auto-register. `BLEPeripheral` covers RSSI, phase, characteristic lookup, and the underlying `CBPeripheral`. Delegate callbacks stay off the public Swift surface. `BZPeripheral+Internal.h`, `BZPeripheralController+Internal.h`, and `BZBLEUtils.h` are private headers.
- The pod is published to CocoaPods trunk from `https://github.com/bingerz/flip-ble-ios.git`. The git tag must equal `s.version` with no `v` prefix. `scripts/release-pod.sh` lints, creates that annotated tag, pushes the branch and tag, runs `pod trunk push --allow-warnings`, then copies the podspec into `Flip-BLE/<version>/` without committing the archive. `--lint-only` skips publish. `pod lib lint` builds at the podspec deployment target, which must stay inside the current Xcode range. Trunk reads the git tag of the root podspec. `Flip-BLE/<version>/` is an untracked archive trunk does not read, and the script ignores that archive plus its own uncommitted edits. Annotated tag lookup must peel `refs/tags/<version>^{}`; `ls-remote` of `refs/tags/<version>` alone returns the tag object, not the commit. `cdn.cocoapods.org` returns HTTP 301 for every spec path, including missing versions; a version is published only after redirects and the spec JSON `version` field matches. A trunk client timeout after validation can still mean the spec landed, so recheck the CDN before treating the push as failed. Flip-BLE 0.5.2 is published (git tag `0.5.2`, iOS 15.0, Swift 5.5); do not trunk-push 0.5.2 again.
- On this machine, system Ruby 2.6 ffi 1.15.5 is x86_64-only and must not be rebuilt with `gem pristine ffi`. `pod --version` does not load ffi. Trunk push updates the CDN through typhoeus/ffi, so `scripts/release-pod.sh` runs pod as `arch -x86_64` when `/usr/bin/ruby` cannot require ffi.
- `BLECentral.scan` keeps the service UUIDs and allow-duplicates flag until the central is `poweredOn`, then starts. `stopScan()` drops that request. If Bluetooth cycles off and on without `stopScan()`, the same parameters scan again. `observeState()` yields the current state on subscribe, then later changes on the same stream. One process has one scan filter; a later `scan` replaces it for every subscriber. Cancelling notify on a characteristic clears every callback for that characteristic.
- The Example app is pure Swift with no bridging header, deployment target iOS 15, Swift 5.5. It must use the UIScene lifecycle (`SceneDelegate`); builds against the current SDK crash at launch without it. Screens import `Flip_BLE` and follow the system appearance with semantic colors and dynamic type.
- With an empty or fully invalid service-UUID filter, the Example scans `1803`, `0900`, `FD44`, `FE2C`, and `FEAA` and shows that fallback. Mixed input keeps the valid UUIDs. Scan starts and stops only from the user. One row per identifier; later advertisements update the name, RSSI, and the saved advertisement summary. Editing the name or identifier filter drops non-matching scanned rows and keeps connecting or connected rows. Disconnecting from a nested device page returns to the scan list.
- Scan filtering, UUID parsing, hex logs, advertisement summaries, GATT property splitting, the console log cache (`DemoConsoleStore`), and Example styling live in `Example/Flip-BLE/DemoSupport.swift`. Simulator tests are `Example/Tests/DemoLogicTests.swift`, `BLEFacadeTests.swift`, and `Tests.swift`.
- Example Write and Write Without Response both call `BLEPeripheral.write`. `BZPeripheralController` uses with-response when the characteristic has `CBCharacteristicPropertyWrite`, and without-response only when that bit is absent. The Swift facade has no write-type parameter.
